# 训练报告：从零用纯 RL 学会起立

本文记录 EEI-RL 的训练配方、实测数据，以及踩过的坑。所有数字都是本项目在本机
（i5-8500，6 核 6 线程，CPU 训练）上跑出来的。

## 1. 配方

| 项目 | 取值 |
| --- | --- |
| 算法 | PPO（Stable-Baselines3 2.9） |
| 策略网络 | MLP `128 → 128`（tanh），输出高斯均值 + 可学习 `log_std` |
| 初始探索 | `log_std_init = −0.5`（std ≈ 0.61） |
| 学习率 | `3e-4`，线性衰减到 0 |
| 采样 | 5 个并行环境 × `n_steps 1024`，`batch_size 1024`，`n_epochs 10` |
| 折扣 / GAE | `γ = 0.99`，`λ = 0.95` |
| 奖励归一化 | `VecNormalize(norm_obs=False, norm_reward=True, clip=10)` |
| 观测 | `[roll, pitch, target1, target2]`（照搬上游，未归一化） |
| 初始状态 | 四个倒伏姿态均匀随机；`--pose-jitter-deg` 可加摆放偏差 |
| 总步数 | 300 万（4/4 在 50 万步首次出现，60 万步后稳定） |
| 训练产物 | 每 10 万步一个 checkpoint，每次评估都写 TensorBoard 与 JSON |

训练速度参考：约 1600–2000 步/秒（含每 5 万步一次的四姿态评估）。

## 2. 奖励是怎么改的

上游奖励（`env/robo1_env.py`，未改动）的关键结构：

```
reward = 2·upright + 8·Δupright − 0.2·(roll²+pitch²)
         − stand_gate·(0.5·Σservo² + 0.2·Σtarget² + 5·foot_err²)
         − 0.01·Σqvel² − 0.005·Σservo_vel² − 0.005·Σaction² − 0.02·ΣΔtarget²
         + 5（当且仅当 goal_pose）
stand_gate = clip((upright − 0.65) / 0.35, 0, 1)
```

### 坑：0.65 处的收益悬崖

`stand_gate` 让「手臂伸着」的代价只在直立度超过 0.65 后才出现。量一下：

* 直立度 0.70、手臂伸着（servo ≈ ±1.5）：收益 ≈ `2×0.7`，代价由门控按比例出现，总收益仍为正；
* 完全直立、手臂伸着：收益 `2×1.0`，代价 `≈ 0.5×2.25 + 0.2×4.8 ≈ 3.2`，**总收益为负**。

于是策略的最优解是**卡在门下方**。实测现象（用上游原奖励从零训练）：

```
100k: upright roll_pos 0.69  roll_neg 0.68  pitch_pos −0.15  pitch_neg 0.73
200k:                   0.70           0.70           −0.15           0.71
300k:                   0.71           0.71           −0.16           0.70     ← 冻住
```

注意 `pitch_pos` 一直是 −0.15，说明它连"侧翻"都没学会；而奖励曲线仍在缓慢上涨——
典型的局部最优。

### 改法（`ShapedEnv`，只改奖励，不动物理与达标判定）

1. **`gate_scale` 从 0 退火到 1**：前期完全不罚手臂，先学会站起来；后期再加压，
   逼它把手收回零位满足完整达标条件。
2. **门函数换成 smoothstep，起点 0.75**：去掉陡崖，给策略连续的梯度。
3. **加 `6·upright⁴`**：0.7 直立得 1.4，1.0 直立得 6，把两者拉开。

### 坑二：站稳之后舵机在抖

第一版跑通 4/4 之后上机，发现机器人**站直以后舵机还在持续抽动**。
把达标期间的轨迹打出来看，是典型的高增益抖振：

```
 step | a1     a2    | t1      t2     | servo1 servo2 | up
   61 | -0.015 -0.713 | -0.104 -0.145 | +0.021 -0.032 | 1.000
   62 | +0.441 -0.421 | -0.068 -0.179 | +0.005 -0.055 | 1.000
   63 | +0.697 +0.013 | -0.013 -0.178 | -0.000 -0.074 | 1.000
   64 | +0.670 +0.414 | +0.041 -0.145 | +0.004 -0.086 | 1.000
   65 | +0.375 +0.634 | +0.071 -0.094 | +0.013 -0.089 | 1.000
```

动作在 ±0.7 之间来回跳，`target` 以约 5 Hz 在 ±0.1 rad 摆动，
于是固件下发的舵机角度 `90 − deg(target)` 跟着来回摆 **9°–13°**（实测量化见下）。
机器人本身是稳的（`up = 1.000`），晃的是控制指令。

原因是原奖励对动作的惩罚太小：`0.005·Σa²`（量级 0.005），
而待在达标状态每步有 ~13 的收益，抖动的代价可以忽略。

**改法**：达标（`goal_pose`）时追加两项

```
reward += hold_bonus · exp(−hold_sharp · Σa²)      # 越静止给得越多（默认 3.0, 10.0）
reward -= hold_action_penalty · Σa²                # 直接惩罚抖动（默认 1.5）
```

标定时有一条硬约束：**达标状态的收益必须始终为正**。
达标本身给 `+5/步`，如果抖动惩罚超过它，策略会宁愿卡在"直立但没达标"的状态。
实测把惩罚设成 `6.0` 时正是如此——`roll_pos` 一直停在
`upright = 0.99`、`servo = 1.4` 就是不达标。改成 `1.5` 之后：

* 抖动时（`Σa² ≈ 1`）：`+5 − 1.5 + 0.0002 ≈ +3.5/步`
* 完全静止时（`Σa² ≈ 0`）：`+5 − 0 + 3.0 = +8.0/步`

两者差 `4.5/步`，方向明确又不会把达标状态变成负收益。

另外还有一个反直觉的点：**不要在"接近直立"时惩罚动作**。
把手臂从 `servo = 1.4` 收回到 0 需要持续输出动作，在那里加惩罚
（实测 `still_action_penalty = 0.5`）会让 `roll_pos` 卡在收臂中途，
所以默认设成 0。

### 静止奖励的效果（实测）

`rl/verify_pure_rl.py` 第 3 节会量化达标状态下的抖动。同一个测试脚本下：

| 指标（达标状态下） | 旧权重（无静止奖励） | 新权重（含静止奖励） | 改善 |
| --- | --- | --- | --- |
| 每步 Δtarget | 0.031 – 0.048 | **0.00018 – 0.00067** | 约 70–170× |
| 动作幅度 `Σ|a|` | 0.41 – 0.62 | **0.003 – 0.009** | 约 70–140× |
| 方向翻转率 | 0.19 – 0.20 | **0.02 – 0.03** | 约 8× |
| **舵机指令摆幅** | 9.2° – 12.7° | **0.27° – 1.12°** | 约 11–46× |

也就是说：达标之后策略基本输出零动作，固件下发的舵机角度几乎不动，
视觉上的"站直后抽动"消失。四个姿态的标准判定仍然是 4/4。

> 复现这份数据的命令：
> ```powershell
> python rl/verify_pure_rl.py --weight rl/weights/eei_pure_rl_v1.zip --offsets=0
> ```

改完之后直立度的变化：

```
 50k: roll_pos 1.00  roll_neg 1.00  pitch_pos −0.15  pitch_neg 1.00   （3 个姿态已站起）
100k:         1.00           1.00            1.00           1.00   （四个都站起，但手臂伸着）
200k:         1.00           1.00            1.00           1.00   （达标 0/4，servo ≈ ±1.55）
300k:         0.96           1.00            1.00           1.00   （3/4，手臂开始收回）
500k:         1.00           1.00            1.00           1.00   （★ 4/4）
600k–1250k:   连续 13 次评估全部 4/4，手臂稳定停在 |servo| < 0.1
```

退火进度与达标数的对应（`gate_scale` 在总进度 0 → 40% 之间线性上升）：

| 步数 | gate_scale | 达标 |
| --- | --- | --- |
| 100k | 0.03 | 0/4（站起来了，但手臂伸着） |

| 500k | 0.17 | 4/4（首次） |
| 600k | 0.20 | 4/4 起稳定 |

## 3. 终验结果

发布权重 `rl/weights/eei_pure_rl_v1.zip`（含静止奖励的那次从零训练，取 50 万步 checkpoint）：

```
=== 1. 四个标准姿态（上游原始判定） ===
  roll_pos   upright=1.0000  goal_pose=True
  roll_neg   upright=1.0000  goal_pose=True
  pitch_pos  upright=1.0000  goal_pose=True
  pitch_neg  upright=1.0000  goal_pose=True
  → 4/4

=== 2. 摆放偏差鲁棒性（每姿态 5×5 组，±10° / ±5° / 0） ===
  roll_pos   25/25
  roll_neg   25/25
  pitch_pos  25/25
  pitch_neg  25/25
  → 合计 100/100

=== 3. 达标后的静止程度（越小越好） ===
  roll_pos   达标步数= 50  每步Δtarget=0.00018  动作均值=0.003  指令摆幅=0.27°
  roll_neg   达标步数= 50  每步Δtarget=0.00035  动作均值=0.005  指令摆幅=0.59°
  pitch_pos  达标步数= 50  每步Δtarget=0.00043  动作均值=0.006  指令摆幅=0.75°
  pitch_neg  达标步数= 50  每步Δtarget=0.00067  动作均值=0.009  指令摆幅=1.12°
```

> 检查自己训练出来的权重时，建议同时看这三节：达标数优先，达标数相同再比摆幅。
> 训练脚本已把 `eval/cmd_swing_mean` 写进 TensorBoard，
> 并按 `(达标数, −摆幅)` 的字典序自动保存 `<tag>_best.zip`，所以直接取 best 即可。

## 4. 复现性验证

我们从零独立训练了三次，都跑到 4/4：

| 次数 | 标签 | 奖励版本 | 首次 4/4 | 摆放偏差 | 达标后指令摆幅 |
| --- | --- | --- | --- | --- | --- |
| 1 | `eei_repro` | 无静止奖励 | 600k | — | — |
| 2 | `eei_v2b` | 含静止奖励 | **500k** | **100/100** | 0.27°–1.12° |
| 3 | `eei_v3` | 含静止奖励（同一条命令） | **500k** | **100/100** | 0.27°–1.12° |

第 2、3 次的权重哈希不同（子进程调度会让 PPO 的采样顺序有细微差异），
但**逐项验证结果相同**——这套配方是稳健收敛，不是靠某个种子撞出来的。

```

## 5. 上机验证

烧进 ESP32-S3 后（固件把 BMI160 读数换算到机身坐标系，再按
`obs=[roll,pitch,target1,target2]` 输入策略）：

* 板上 50 Hz 策略任务正常运行，`/imu` 里能看到 `t1/t2` 实时变化，
  舵机指令符合 `angle = 90 − deg(target)`；
* 把机器人从 pitch −19.8° 的状态交给策略，几十毫秒内被拉平到 −0.23°，
  并保持直立（`az ≈ −0.999`）。

## 6. 顺带搞清楚的几件事（供参考）

1. **上游发布的那份权重没有经过 PPO。** 它的元数据是 `num_timesteps=0`、
   `_n_updates=0`、`log_std=[0,0]`、优化器状态为空——和
   `pretrain_robo1_from_scripted.py`（纯监督克隆，用脚本自己的 Adam）的输出完全一致，
   而与真正跑过 PPO 的权重（`_n_updates=660`、`log_std≈−0.24`、优化器 84 KB）处处不同；
   上游仓库里那份 `robo1_getup_ppo.zip` 的提交时间也比训练脚本早两天。
   也就是说 README 描述的 PPO 步骤在发布权重上并没有体现。
2. **克隆阶段不含 RL。** 它是拿脚本轨迹做动作均值的 MSE 回归，没有奖励、没有环境交互、
   没有价值函数（critic 全程停在随机初始化）。我们用逐层权重距离量过：
   克隆阶段只有 actor 路径的参数在变。
3. **从零训练时，PPO 的"温和模式"几乎没有改变策略。** 从克隆权重出发做
   lr 3e-5、std 0.135 的 PPO，2 万步后 actor 各层只变化 0.09%–0.24%，
   而 critic 变化 6%–11%（对照组：两个独立克隆之间每层差 100%+）。
   所以那种"PPO 后仍保持 4/4"其实主要是没怎么动策略。
